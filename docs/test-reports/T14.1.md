# Test report T14.1 — Lần 1
Kết luận: **PASS (còn phần chờ Mac/thiết bị)**

Mọi test chạy được trên máy này đều xanh: sinh lại Pigeon giống từng byte, analyze, Dart (dev + prod), Kotlin JVM (dev + prod), Swift
typecheck (iOS 15 simulator + device, strict concurrency). Trên emulator `napstop_api34` còn chạy thêm V11 qua validator native,
`deviceStatus()` ở 5 trạng thái DND/pin và `engineParamsJson` sau khi process chết thật. Không có lỗi trong code T14.1. Còn chờ: máy
thật API 30+ (`priorityAllowsAlarms = false`, các mức âm lượng báo thức), máy API 26–29, và iOS (XCTest mới chỉ được typecheck).

Môi trường: Windows 11 Home 10.0.26200, Git Bash; Flutter 3.47.8 (Dart 3.13.7) tại `D:\src\flutter`, `PUB_CACHE=/d/src/pub-cache`;
JDK MS OpenJDK 17, Gradle 9.3.1; emulator `napstop_api34` (Android 14, API 34, WHPX, app targetSdk 36), không có máy thật; Swift 6.4.1 +
Darwin SDK 27.1 trong WSL Ubuntu (gồm `XCTest.framework` của simulator).

Câu hỏi của tester: "Có tình huống nào khiến app không đánh thức người dùng đúng lúc không?" T14.1 không đổ chuông, nhưng
`deviceStatus()` là nguồn để T22/T25 cảnh báo trước chuyến. Emulator xác nhận một tình huống thật: ở **"Im lặng hoàn toàn"** (DND
`none`) Android tắt tiếng luồng báo thức (`alarmMuted = true`, `alarmVolumePct = 0`). Hàm trả đúng dữ liệu này, T22/T25 phải dùng nó để
cảnh báo (xem O1). V11 không chặn nhầm cấu hình hợp lệ: đếm theo UTF-16 ở cả 3 nền tảng, biên 16 384 được nhận. Tham số engine đi
nguyên văn qua snapshot và qua cả lần process chết thật, nên chuyến được khôi phục vẫn dùng đúng ngưỡng.
