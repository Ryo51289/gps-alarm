# T17.3 — Kênh báo bằng thông báo khi không có AlarmKit (iOS 16–25, hoặc AlarmKit bị từ chối/chưa cấp)

Trạng thái đề xuất: **spec-ready**.

Ngày: 2026-11-06. Nguồn: `docs/PLAN-ios.md` §5 (T17.3), §8.1; `docs/spikes/S3.md` §4.1, §5.2 (S3-9…11), §6.4 (`NotificationChannel`), K2 (C3),
K3, K4 #7, #13–#15, #20, H4; `docs/test-reports/S3.md` #3, #8; `docs/specs/T17.md` D14, §4.2, §5.6.4, §5.6.6, §5.8, R1, R2;
`docs/test-reports/T17.md` **O7** (thông báo đã hiện có trạng thái `other`, không phải `alerting`), O8; `docs/specs/T17.2.md` D10 (file âm
28–29,5 s); `docs/specs/T28.3.md` D5 (UI nói rõ không kêu khi Im lặng). Mã: `NapStopIOS/SystemAlarmsIOS.swift` (`NotificationSystemAlarms`,
`SystemAlarmsRouter`), `TripRuntime/{SystemAlarms,AlarmUpdateInterpreter,EffectPlanner,TripRuntime}.swift`.

## Bối cảnh & mục tiêu

- PRD §4: iOS 26+ báo bằng AlarmKit; iOS cũ (hoặc AlarmKit bị từ chối) báo bằng thông báo Time Sensitive + âm tuỳ chỉnh. S3 H4 (kỳ vọng, chưa đo):
  thông báo **không kêu khi máy để Im lặng** (chỉ Critical Alerts vượt được nút Im lặng); vượt Tập trung chỉ khi có capability Time Sensitive và
  người dùng cho phép. T28.3 đã nói rõ giới hạn này trên UI (`homeChipIosSilentRisk`, `alarmSettingsStyleRingHintNoSilent`).
- T17 §5.6.6 có kênh thông báo **tối thiểu**: một thông báo, âm `.default`, và `list()` báo thông báo đã hiện là `.other`. Hệ quả (tester T17 O7):
  runtime không nhận ra báo dự phòng qua thông báo đã kêu (không `FallbackFired`, không huỷ khe khác theo K4 #3, không `AlarmSilenced`).
- Mục tiêu: kênh thông báo đủ dùng làm kênh báo thứ hai — âm dài, lặp 3 lần, nhận biết đúng trạng thái "đang kêu", và chạy S3-9…11 trên máy.

## Phạm vi

**Làm**
1. Một "alarm logic" của kênh thông báo = **3 request** cách nhau 30 s (S3 `TS_REPEAT = 3`, `TS_REPEAT_INTERVAL_S = 30`), âm 28–29,5 s của T17.2.
2. Ánh xạ trạng thái thuần cho thông báo: `scheduled` / `alerting` / `other` theo cửa sổ thời gian (sửa O7).
3. Hẹn kiểm danh sách đúng các mốc kêu (kênh thông báo không có luồng cập nhật như `alarmUpdates`).
4. `list()` không còn trả `nil` cho kênh thông báo khi AlarmKit đọc lỗi (sửa O8).
5. Giới hạn số request đang chờ (64/app) và test bảo đảm không vượt.
6. Giao thức S3-9…11 trên iPhone 16 Plus (iOS 27, tắt AlarmKit để buộc kênh này).

**KHÔNG làm**
- **Không thêm entitlement Time Sensitive** (`com.apple.developer.usernotifications.time-sensitive`) trong T17.3: cần tài khoản Apple Developer
  trả phí (S3 K3: bản ký Apple ID miễn phí báo `timeSensitiveSetting = notSupported`). Thêm ở **T40.1**; phần "vượt Tập trung" kiểm ở T40.
- Không Critical Alerts (cần Apple duyệt, S3 K3). Không nút hành động trên thông báo (Câu hỏi mở 2). Không đổi AlarmKit, engine, Pigeon, Dart.

### 2. Kiểu dữ liệu (thuần, `TripRuntime/NotificationAlarm.swift`)

```swift
public enum NotificationAlarmPlan {
    public static let repeats = 3                    // TS_REPEAT
    public static let repeatIntervalMs: Int64 = 30_000
    public static let alertWindowMs: Int64 = 90_000  // 2·30 s + 30 s
    /// Fire times (wall ms) of the requests of one logical alarm.
    public static func fireTimes(_ fireAtWallMs: Int64) -> [Int64]          // [f, f + 30 000, f + 60 000]
    public static func requestId(_ logicalId: String, rep: Int) -> String    // "\(id)#\(rep)"
    public static func parse(_ requestId: String) -> (logicalId: String, rep: Int)?
}
public enum NotificationAlarmState {
    /// `pendingReps`/`deliveredReps`: reps (0…2) of one logical alarm in pendingNotificationRequests / deliveredNotifications.
    public static func state(fireAtWallMs: Int64, pendingReps: Set<Int>, deliveredReps: Set<Int>, nowWallMs: Int64) -> SystemAlarmState
}
public struct SystemAlarmList: Sendable, Equatable {               // D6; SystemAlarms.list() trả kiểu này (nil chỉ khi mọi kênh lỗi)
    public let items: [SystemAlarmInfo]
    public let alarmKitUnreadable: Bool
}
```
Bảng `state`:

| `deliveredReps` | `pendingReps` | `now < fire + 90 s` | Kết quả |
|---|---|---|---|
| ∅ | ≠ ∅ | — | `scheduled` |
| ∋ 0 (hoặc ≠ ∅) | bất kỳ | có | `alerting` |
| ≠ ∅ | bất kỳ | không | `other` |
| ∅ | ∅ | — | (không có trong danh sách) |

`NotificationSystemAlarms.list()` gom request theo `logicalId` rồi gọi `state`; `fireAtWallMs` lấy từ `userInfo` của bất kỳ request nào (của `#0`).

### 3. Runtime (bổ sung T17)

- `SystemAlarmRequest` có `channel == .notification` → `NotificationSystemAlarms.schedule` đặt 3 request (D1, D2, D3, D10); lỗi ở request nào → huỷ
  các request vừa đặt của alarm logic đó rồi ném (không để alarm logic nửa vời).
- `ring()`/`scheduleSlot()` với kênh thông báo: thêm `deferred(.notifPoll)` theo D5. `interpretUpdates` không đổi: nay thông báo có `alerting` nên
  nghĩa vụ 5 (`FallbackFired` + huỷ khe khác), K4 #3 ("now" kêu → huỷ khe), nghĩa vụ 6 (`AlarmSilenced` khi rời `alerting`) chạy được.
- Khôi phục (T17 §5.8, R2): alarm logic kênh thông báo `alerting`/`other` (đã giao) của chuyến → coi như **đã kêu** (`RANG`), không kêu lại (R2 bước 1).
- Chọn kênh (T17 D14) không đổi: AlarmKit khi iOS 26+ và `authorized`; còn lại thông báo nếu được cấp. AlarmKit chuyển sang `authorized` giữa chuyến
  → lần đặt sau dùng AlarmKit, khe thông báo cũ bị huỷ theo A/B.

### 4. UI

Không thêm (T28.3 đã có): thẻ "Sẵn sàng" `homeChipIosSilentRisk`, màn 3 `alarmSettingsStyleRingHintNoSilent`, màn 4 `trackingTileAlarmIosSilentRisk`.
T17.3 chỉ xác nhận trên máy (S3-10) rằng câu chữ đúng với thực tế đo được; nếu S3-10 cho thấy **có** kêu khi Im lặng thì báo designer sửa copy.

### 5. Riêng tư, pin, a11y

`userInfo` chỉ id/thời điểm; tiêu đề thông báo có tên đích (như tiêu đề AlarmKit, T17 §8). Hẹn kiểm D5 tối đa 4 lần mỗi alarm logic (không tốn pin
đáng kể). Thông báo là UI hệ thống (VoiceOver đọc tiêu đề).

## Câu hỏi mở

1. **Số lần lặp và khoảng cách** (D1). A (đề xuất, đã áp): 3 lần cách 30 s (≈ 90 s chuông, như S3). B: 5 lần (≈ 2,5 phút; tốn ngân sách 64). Đề xuất: **A**;
   xem lại sau NM01.
